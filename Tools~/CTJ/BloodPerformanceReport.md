# 혈흔 이펙트 성능 측정

측정일: 2026-11-23. 현재 혈흔은 Lean Pool로 재사용되지만, 개별 혈흔의 이동·충돌 검사와 트레일 메시 갱신은 재생 중 계속 실행된다. 풀링은 생성 시 CPU·메모리 비용을 줄였고, 대량 동시 재생의 CPU 비용까지 없애지는 않았다. 이 작업에서는 혈흔 개수나 물리·트레일의 동작을 줄이는 최적화는 적용하지 않았다.

측정 후 사망 분사 속도 배율을 1.8에서 1.25로 조정했다. 아래 표와 원본 데이터의 `current`는 측정 당시의 1.8배 설정이며, 1.25배로 다시 측정한 결과는 아니다.

## 환경과 비교 방법

- Unity 6000.3.22f1, Windows Editor Play Mode, Direct3D12.
- Intel Core i9-14900HX, RTX 4060 Laptop GPU, RAM 약 32GB.
- EnemyTestScene에서 기존 게임 오브젝트를 잠시 비활성화하고 임시 바닥·벽·천장, 정사영 카메라와 혈흔만 사용했다. 전체 게임 플레이 성능이 아닌 이펙트 집중 부하 측정이다.
- 1280×720 RenderTexture, 정사영 크기 6, VSync 해제, 프레임 제한 없음, Fixed Timestep 0.02초. 측정 후 설정을 복원했으며 씬은 저장하지 않았다.
- 현재 사망 혈흔: 기본 52~64개에 임시 피드백의 개수 2배·속도 1.8배를 적용한 104~128개/이펙트. 360도 방출, 바닥·벽 접촉, 흔적과 트레일을 포함한다.
- 이전 양의 비교군: 개수·속도 배율 1, 52~64개/이펙트. 현재 구현의 동일한 재생 코드로 실행했다.
- 생명주기 비교는 `Instantiate/Destroy`와 충분히 생성·재생·반환한 Lean Pool의 재사용을 비교했다. Git의 `d03d3026` 풀링 도입 전 코드를 확인해 생성/삭제 방식을 재현했다. **과거 실행 당시의 FPS 기록을 복원한 결과는 아니다.** 같은 양의 혈흔에서 풀링 유무를 비교하는 A/B 실험이다.
- 1·10·30묶음 동시 방출 × 두 가지 입자 양 × 풀링 유무 × 각 5회 = 60회. 여기에 혈흔 없는 기준 5회와 현재 30묶음 4초 관찰 10회를 더해 **총 75회, 14,876프레임**을 수집했다. 짧은 관찰은 회당 0.9초이며 파일 내 pilot 2회는 집계에서 제외했다.
- 비어 있는 풀의 첫 생성도 1·10·30묶음씩 5회, 별도로 15회 측정했다. 같은 반복의 두 방식은 같은 난수 시드로 입자 수를 맞추고 순서를 번갈아 실행했다.

아래 시간은 ms이며 5회 평균이다. **Main P95는 각 반복에서 구한 프레임 시간의 95백분위수를 다시 평균한 값**이다. 전체 샘플을 합친 단일 95백분위수가 아니다. 에디터 메인 스레드 비용이며 FPS로 직접 환산하지 않는다.

## 현재 사망 혈흔: 풀링 유무

| 동시 묶음 | 평균 총 입자 수 | 생성: 생성/삭제 | 생성: 풀 재사용 | Main P95: 생성/삭제 | Main P95: 풀 재사용 | 풀 재사용 GPU 평균 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 112.2 | 0.655 | 0.204 | 5.229 | 6.695 | 0.285 |
| 10 | 1,148.0 | 2.824 | 1.108 | 9.218 | 9.394 | 0.388 |
| 30 | 3,482.8 | 8.064 | 2.896 | 19.268 | 18.960 | 0.848 |

30묶음에서 생성 구간은 평균 약 64% 줄었다(약 2.8배 빠름). 하지만 재생 중 Main P95는 거의 같았다. 1묶음에서는 풀 재사용 쪽 Main P95가 더 높기도 했으므로, 생성 시간이 줄었다는 이유로 전체 프레임률도 같은 비율로 좋아졌다고 해석하면 안 된다. 혈흔 없는 기준은 Main 평균 4.866ms, P95 평균 5.683ms로 에디터 자체 변동도 존재한다.

현재 30묶음 풀 재사용의 반복별 Main P95는 17.946~20.911ms였다. 60fps의 프레임 예산 16.67ms보다 높은 CPU 프레임이 나타났으며, 전체 게임 로직을 추가할 여유까지 고려하면 이 수준의 동시 혈흔은 성능 문제를 일으킬 가능성이 있다. 1·10묶음에서는 이 테스트의 Main P95가 그 예산 이내였지만, 실제 게임이나 다른 사양에서도 안전하다는 보장은 아니다.

## 이전 양과 현재 양

| 입자 양 / 동시 묶음 | 평균 총 입자 수 | 생성/삭제 생성 시간 | 풀 재사용 생성 시간 | 풀 재사용 Main P95 | 풀 재사용 혈흔 코드 P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 이전 양 / 1 | 57.8 | 0.550 | 0.204 | 6.108 | 0.281 |
| 이전 양 / 10 | 585.8 | 2.282 | 0.629 | 7.679 | 2.028 |
| 이전 양 / 30 | 1,716.2 | 6.026 | 1.699 | 12.529 | 6.573 |
| 현재 양 / 30 | 3,482.8 | 8.064 | 2.896 | 18.960 | 12.379 |

혈흔 코드 P95는 `CTJ.Blood.FixedUpdate` 마커의 렌더 프레임 내 누적 시간이다. 한 프레임에 FixedUpdate가 여러 차례 실행될 수 있다. 현재 30묶음의 혈흔 코드 최대 프레임 누적값은 전체 반복 중 17.193ms였다. 이 값은 하나의 FixedUpdate 호출 시간과 다르다.

이전 양의 풀 재사용 대비 현재 양은 혈흔 코드 P95가 약 1.9배였다. 개수 증가와 속도 증가가 함께 적용된 비교이므로 개수만의 영향으로 단정할 수는 없지만, 풀링을 해도 활성 입자의 계산 비용이 남는다는 것은 확인된다.

## 재생 중 비용과 바닥 흔적

현재 30묶음 풀 재사용에서 이펙트 한 묶음의 FixedUpdate 1회 평균은 0.312ms였으며 그 안의 트레일 갱신은 0.209ms, 약 67%였다. 코드상 공중 입자에 `Physics2D.CircleCast`를 수행하고 트레일 정점·색·삼각형 및 메시를 갱신한다. 측정상 트레일 갱신 비중이 크며, GPU 평균이 0.848ms인 점까지 보면 이 조건에서는 GPU보다 CPU 비용을 먼저 살필 필요가 있다. 트레일을 끈 별도 A/B 실험은 하지 않았으므로 이 비율만큼을 제거 가능한 비용이라고 보지는 않는다.

현재 30묶음을 4초씩 관찰한 추가 측정:

| 방식 | Main 평균 | Main P95 | 혈흔 코드 P95 | GPU 평균 | 2.6초 이후 혈흔 평균 / P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 생성/삭제 | 8.708 | 16.350 | 9.513 | 0.624 | 1.549 / 5.361 |
| 풀 재사용 | 8.953 | 16.190 | 9.451 | 0.612 | 1.658 / 5.464 |

2.6초 이후에는 많이 착지한 단계라 트레일 평균이 풀 재사용 기준 0.089ms/렌더 프레임으로 감소했지만, 혈흔의 상태·표면 추적·출력 계산은 남았다. 이 구간에 모든 입자가 바닥에 붙었다고 개별 검증한 것은 아니므로 ‘바닥 흔적만의 비용’으로 단정하지 않는다. 실제 씬에서는 최근 몇 초간 발생한 피격 혈흔과 사망 혈흔이 겹쳐 누적될 수 있다.

## 첫 생성과 메모리

| 현재 양 동시 묶음 | 빈 풀의 첫 생성 평균 | 첫 생성 범위 | 재사용 생성 평균 | 생성/삭제 시 Mono 사용량 증가 근사치 | 재사용 시 증가 근사치 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 0.878 | 0.596~1.464 | 0.204 | 84KB | 0KB |
| 10 | 3.436 | 2.800~3.953 | 1.108 | 840KB | 0KB |
| 30 | 8.921 | 6.703~10.795 | 2.896 | 2,520KB | 0KB |

빈 풀의 첫 생성은 오히려 일반 생성보다 비쌀 수 있다. 풀링의 이득은 이미 확보된 인스턴스와 배열·트레일 버퍼를 다시 사용할 때 발생한다. 반환해도 메모리를 바로 해제하는 구조가 아니므로 최대 사용량만큼 풀의 비활성 객체가 남는다. 이번 30묶음 측정에서는 반환 후 30개를 보유했다. 84KB 등은 Mono 사용량 변화일 뿐 전체 네이티브·GPU 포함 보유 메모리를 뜻하지 않는다.

메모리 수치는 `Profiler.GetMonoUsedSizeLong()`의 생성 전후 차이로 **정확한 할당 바이트 수가 아닌 근사치**다. 이 에디터의 `GC.GetAllocatedBytesForCurrentThread()`는 1MiB를 할당하는 보정 실험에도 0을 반환하여 사용하지 않았다. 별도의 프레임 GC 카운터는 에디터 활동까지 포함한다. 현재 30묶음에서는 프레임 GC 평균이 생성/삭제 131.45KB, 풀 재사용 16.55KB였고 혈흔 없는 기준은 16.19KB였다. 재사용의 0KB 근사치를 ‘게임 전체 무할당’으로 해석하지 않는다.

측정 구간 중 세대별 GC 수집 횟수는 모두 0이었다. 각 반복 전 수행한 강제 GC는 측정에서 제외했다. 짧은 구간의 결과이므로 장시간 플레이에서 GC가 발생하지 않는다는 의미는 아니다.

현재 개별 버스트는 최대 128입자로 제한되지만 전역 활성 혈흔 수 제한은 없다. EnemyParticleModule의 동시 이펙트 제한은 적 하나 기준이므로 여러 적이 사망할 때의 총량 제한을 대신하지 않는다.

## 해석의 한계와 다음 선택지

- Editor 결과이며 실제 빌드·저사양 기기의 성능 기준값은 아니다. Scene/Game 뷰와 에디터 자체, OS 작업이 메인 스레드와 프레임 시간에 영향을 준다. 세션에는 다른 Unity 프로젝트도 열려 있었고 외부 작업을 통제하지 않았으므로, 출하 성능 판단에는 단독 실행한 빌드에서 다시 측정해야 한다.
- `Main Thread`와 GPU 카운터는 에디터가 제공하는 마지막 프레임 샘플을 수집한다. 개별 생성 호출의 Stopwatch 시간과 동일한 구간을 뜻하지 않는다.
- 반환 시간은 반환/삭제 **요청** 구간이다. `Destroy`의 실제 지연 삭제 비용 전체를 포함하지 않는다. 원본 JSON의 `cleanupMainMaxMs`에는 이후 3프레임도 별도로 기록했지만 에디터 전체 비용이므로 순수 삭제 비용으로 표시하지 않았다.
- 단발 피격, 금속 파편, 다른 해상도, 수십 초간 연속 처치는 이번 표의 대상이 아니다. 현재 사망 혈흔 버스트 중심의 부하 비교다.
- 이 측정 때문에 현재 연출 수치를 임의로 줄이지 않았다. 추가 최적화가 필요하다면 전역 활성량 제한/오래된 흔적 정리, 트레일 갱신 빈도와 샘플 수 조절, 정지한 흔적의 반복 갱신 감소를 각각 별도 A/B로 검증하는 것이 다음 후보다.

## 직접 재현

일반 확인은 EnemyTestScene에서 Enemy18을 처치해 혈흔을 보고, 여러 Enemy18을 같은 시간에 처치하여 Profiler의 `CTJ.Blood.FixedUpdate`와 `CTJ.Blood.Trails`를 확인한다. 다른 적의 AI·UI·사운드 등도 실행되는 일반 테스트는 위 표와 조건이 다르다.

자동 반복은 프로젝트 루트의 PowerShell에서 아래 명령을 사용한다. 현재 씬을 직접 저장하고 Play Mode를 종료한 뒤 Unity Pipeline 서버를 켠다. 도구는 기존 결과 JSON을 덮어쓰므로 기록을 남기려면 먼저 복사한다. 새 실행 후 CSV/이 문서의 기존 표는 자동 갱신되지 않는다.

```powershell
unity command script run --file 'Tools~/CTJ/BloodPerformanceBenchmark.cs' --entry BloodPerformanceBenchmark.Enter --timeout 30 --result-only --json
# Play Mode 진입이 끝난 뒤:
unity command script run --file 'Tools~/CTJ/BloodPerformanceBenchmark.cs' --entry BloodPerformanceBenchmark.Setup --timeout 30 --result-only --json
```

같은 명령의 `--entry`를 순서대로 `BloodPerformanceBenchmark.Baseline`, `Legacy1`, `Legacy10`, `Legacy30`, `Current1`, `Current10`, `Current30`, `Steady30`, `ColdStart`로 바꿔 각 호출이 끝난 뒤 다음 호출을 실행한다. 각 이름에 `BloodPerformanceBenchmark.`를 붙이고 `--timeout 50`을 사용한다. 완료 또는 실패 후에는 `Cleanup`, `Exit` 순서로 호출하고 Edit Mode 전환이 끝난 뒤 `Restore`를 호출한다. 이 도구가 시작한 Play Mode만 종료하며 사용자의 실행 중인 게임에서는 실행하지 않는다.

결과 파일:

- [원본 JSON](BloodPerformanceResults_2026-11-23.json): 개별 반복, 평균·중앙값·P95·최대, CPU/GPU/GC 및 정리 후 프레임.
- [요약 CSV](BloodPerformanceSummary_2026-11-23.csv): pilot 제외, 같은 조건 5회 평균과 반복별 범위.
- [측정 도구](BloodPerformanceBenchmark.cs): 저장되지 않는 런타임 시험 환경과 측정 코드.

## 사용한 문법과 이유

- `ProfilerMarker`는 혈흔 전체 갱신과 그 안의 트레일 구간에 이름을 붙인다. `using var sample = marker.Auto()`는 메서드를 빠져나갈 때 Dispose를 호출해 측정 구간을 닫는 C# 문법이다. 프레임마다 Stopwatch 객체를 만들지 않고 Unity Profiler에서 구간을 볼 수 있다.
- `ProfilerRecorder`는 위 마커와 Main Thread·GPU·프레임 GC를 수집한다. 프레임 내 호출을 합산하므로 한 프레임에 FixedUpdate가 여러 번 실행되는 경우도 포함한다.
- 도구의 `async Task`와 `await Awaitable.NextFrameAsync()` / `EndOfFrameAsync()`는 에디터를 멈추지 않고 다음 프레임까지 기다린다. 외부 도구 실행용 코드이며 새 게임 코루틴을 추가한 것은 아니다.
- `try/finally`로 측정 오류 때도 남은 이펙트를 반환하고 난수 상태를 복원한다. 전체 실행 후 `Cleanup`은 렌더 텍스처와 시험 오브젝트 및 런타임 설정을 정리한다.
- 비공개 메서드는 시작 시 Reflection으로 delegate에 연결한다. 측정 루프마다 `MethodInfo.Invoke`로 인수 배열을 만드는 비용을 넣지 않고 실제 생성·재생 경로를 비교하기 위해서다. 게임의 공개 API는 늘리지 않았다.
- 기존에 설치된 Newtonsoft.Json으로 반복 목록과 결과를 JSON에 저장했다. 새 패키지를 설치하지 않았다. 도구는 Unity가 자동 임포트하지 않는 `Tools~/CTJ`에 있어 빌드에 포함되지 않는다.
